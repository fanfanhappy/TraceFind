# TraceFind · 模块五实现（快速预览）

模块四已经把正文抽出来了，这一阶段把它接到界面上：选中结果按 `Space`，
右侧抽屉直接显示内容——文本滚动到命中处、图片直接看、Office 复用抽取器。

- 版本：0.5.0（M5）
- 入口：`src-tauri/src/preview.rs`（数据）、`src/components/PreviewDrawer.tsx`（界面）

## 一、数据流

```
预览打开（Space）
   → preview_file(path)
       ├─ 图片：读字节 → base64 data URL（上限 8 MB）
       ├─ 文本/Office/PDF：复用 extract::extract
       └─ 其它：直接判为不支持
   → 前端渲染：文本高亮 + 滚动到第一处命中；图片贴图
```

抽屉内容**跟随选中项**：打开后按 `↑` `↓` 会实时切换预览，不用反复按 Space。
这比"每次都要重新打开"更接近 Finder / Everything 的手感。

## 二、界面细节

| 状态 | 表现 |
|---|---|
| 文本 | 12px 正文、1.7 行高；代码类用等宽字体（按扩展名判定语言） |
| 图片 | 居中、最大宽度撑满、圆角；透明图有底色 |
| 命中 | 关键词高亮，渲染后自动 `scrollIntoView` 到第一处命中 |
| 截断 | 超过 12 万字符只回传前段，底部提示"已截断" |
| 不支持 | 明确写出原因（如「EXE 文件不支持内置预览」），并提示用外部程序 |
| 加载 | 读取中显示 spinner |

预览打开时列表会变窄，因此自动隐藏结果行的 `Enter/Space` 操作提示，把宽度让给文件名。

## 三、几处必须处理的问题

**长文档的高亮节点**：一篇 12 万字的文档里，像"的"这种词可能上千处。
每处生成一个 `<mark>` 会把渲染拖垮，所以高亮上限设为 200 处，其余照常显示但不标记。

**二进制文件**：早期实现里未知扩展名会走纯文本解码，`.exe` 会被当作文本读进来显示乱码。
现在先判断 `extract::supports()`，不支持的直接返回 unsupported。

**解析器崩溃**：PDF 解析库遇到不支持的编码会 panic，和模块四一样用 `catch_unwind`
隔离，前端看到的是"解析器崩溃（编码不受支持或文件损坏）"，不会拖垮主进程。

**图片不过 asset 协议**：预览走 base64 data URL，省掉为一个功能单独开 asset 协议与权限。

## 四、实测

| 场景 | 结果 |
|---|---|
| DOCX（3632 字符） | kind=text，含命中词，滚动定位正常，7 处高亮 |
| Markdown（4748 字符） | kind=text，language=markdown |
| PNG（67.8 KB） | kind=image，data URL 正确渲染 |
| EXE | kind=unsupported，「EXE 文件不支持内置预览」 |
| 中文 PDF（CID 编码） | kind=error，「解析器崩溃（编码不受支持或文件损坏）」 |

## 六、已知边界

1. **不做语法高亮**：代码只换等宽字体，没有词法着色。
2. **PDF 不渲染版面**：只显示抽出的文字，图片型 PDF 无内容可显示。
3. **没有缩放/翻页**：图片按宽度自适应，长图需要滚动。
4. **长文本一次性渲染**：12 万字符以内直接铺 DOM，没有虚拟滚动；再长会截断。
5. **不缓存**：每次切换选中都重新读取，PDF 这类解析较慢的文件切换时会有可感知延迟。
